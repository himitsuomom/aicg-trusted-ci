# AICG trusted CI

This public repository stores the trusted Buildkite dashboard YAML and isolated Semantic Verifier runner for `himitsuomom/ai-coding-governance-platform`. The mechanical `aicg-trusted-gate` check is active and required by protected `main` alongside GitHub Actions. The authenticated verifier remains disabled until its separate pipeline, pinned verifier policy, and Buildkite secrets are provisioned.

## What the check means

The dashboard YAML validates the Buildkite checkout SHA, pins the target policy and dependency lockfiles by SHA-256, downloads only hash-locked binary dependencies, audits the runtime lock in a networked container that never receives PR source, and runs the target's configured checks in an isolated container with network disabled. The PR container receives no host environment, Buildkite credentials, GitHub credentials, Docker socket, or authenticated `.git` directory. It runs on an ephemeral Buildkite-hosted Linux agent, with CPU, memory, process, and time limits. Host-side artifact upload skips symlinks, refuses individual evidence files larger than 10 MiB, and caps combined uploaded-path size at 50 MiB, including sparse files and hard links.

The mechanical step protects CI credentials from ordinary malicious PR code. The target's application, CLI, test suite, and evidence are still PR-controlled; a green mechanical run cannot prove code benign.

The Semantic Verifier is a separate `aicg-semantic-verifier` pipeline triggered only after the mechanical step passes. It skips Buildkite checkout so PR-controlled `.buildkite/hooks` never run in its credential-bearing job. The fixed trusted command fetches the exact PR-head commit as data, downloads evidence from the triggering build, checks source/policy/run binding, and fetches AICG code at an immutable commit. It never installs or imports code from the PR. It uses the existing `linux-small` queue so the design remains compatible with Buildkite Free.

Only this child pipeline reads `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, and `AICG_VERIFIER_PRIVATE_KEY` using `buildkite-agent secret get`. Restrict every secret policy to all three first-party claims: the verifier pipeline's `pipeline_id`, the `linux-small` queue's `cluster_queue_id`, and `build_source: trigger_job`. Do not grant access to the parent `aicg-trusted-gate` pipeline. The verifier policy also checks the triggering pipeline before it retrieves secrets. Do not put secret values in YAML, environment settings, plugins, or uploaded artifacts.

The signed report binds the exact source, policy, run, verifier input, provider, and model. The trusted package imports the report and runs the final gate; any non-PASS decision, invalid signature, missing secret, provider error, or free-quota exhaustion fails the step. Candidate evidence remains untrusted input even after its hashes are checked. The reviewer can miss defects and does not prove code benign.

The status context reserved for this step is `buildkite/aicg-semantic-verifier/pr`. Keep it optional until the policy requires authenticated verification, the verifier queue and secret access policies are in place, and a live signed PASS has been observed. Then require this exact Buildkite-App status in addition to the existing checks on protected `main`.

## Buildkite setup

1. Connect the Buildkite organization to GitHub using the **Buildkite GitHub App with full access**, with **Only select repositories** set to exactly `himitsuomom/ai-coding-governance-platform` and `himitsuomom/aicg-trusted-ci`. The first hosts the target gate; the second needs an independent Buildkite status for changes to this public trusted-runner repository. Do not select all repositories. The app requests read access to actions, actions variables, code, environments, and metadata, and read/write access to artifact metadata, attestations API, checks, commit statuses, deployments, issues, packages, pull requests, and repository hooks. It does not request repository-content write access.
2. Keep the existing `aicg-trusted-gate` pipeline on the target repository and the default cluster. It uses `linux-small` for candidate tests and receives no Buildkite secrets.
3. Create a second pipeline named `aicg-semantic-verifier` for the same repository and cluster. Use the existing `linux-small` queue. Disable direct branch and pull-request webhook builds; this pipeline is started only by a trigger from `aicg-trusted-gate`.
4. Paste [`pipeline.yml`](pipeline.yml) into the `aicg-trusted-gate` dashboard **YAML Steps** editor and [`verifier-pipeline.yml`](verifier-pipeline.yml) into the verifier pipeline's dashboard YAML Steps editor. Do not use Pipeline Upload or load `.buildkite` from the target repository. The verifier pipeline has `checkout.skip: true` and runs only when Buildkite identifies `aicg-trusted-gate` as the trigger source.
5. Enable pull-request builds on the parent pipeline, including **Allow builds from third-party forked repositories**. The parent receives no Buildkite secrets; its candidate code runs in the network-disabled container.
6. Wait for a successful parent Buildkite check on a test PR. In the target repository's `main` branch protection, require the exact status from the Buildkite App as well as the existing GitHub Actions `gate`. Require the expected app source, not just a check name.
7. The separate `aicg-trusted-ci-checks` pipeline validates pull requests for this repository. Its YAML is stored in Buildkite, skips checkout, fetches the exact PR head as data, and runs candidate tests in a network-disabled container without secrets. GitHub App access does not install the build-trigger webhook: in `himitsuomom/aicg-trusted-ci` → **Settings → Webhooks**, configure the Buildkite pipeline URL with content type `application/json` and only the **Pushes** and **Pull requests** events. Verify a successful delivery and a Buildkite PR check before requiring its status. The first successful PR status has been observed, and protected `main` now requires `buildkite/aicg-trusted-ci-checks` from GitHub's Buildkite App (app ID `805657`) with branches required to be up to date. Never commit the webhook URL. Never run trusted-runner PR code in the credential-bearing `aicg-semantic-verifier` pipeline.

For Semantic Verifier activation, create a Cloudflare API token scoped to the target account with only the Workers AI `Read` and `Edit` permissions required by the REST API. Add the three secrets above in the default cluster. Apply this first-party access policy to each secret; all three claims must match:

```yaml
- pipeline_id: "01a0f787-2862-43c7-ad5b-d9ab1327da47"
  cluster_queue_id: "2d38e6bd-3cd5-4891-9663-ec5c0d683633"
  build_source: "trigger_job"
```

The IDs match the current `aicg-semantic-verifier` pipeline and `linux-small` queue. Recheck them if either is recreated. Add the public Ed25519 key, issuer, provider, and model to the target `policy.yaml`, set `independent_verification_required: true`, update the runner's pinned policy SHA-256, update both dashboard YAMLs from this repository, and change the parent YAML's `AICG_VERIFIER_ENABLED` value from `false` to `true`. The first successful signed PR run must publish `buildkite/aicg-semantic-verifier/pr` before it is added as a required GitHub check. Keep the secret values out of chat and source control.

The current GitHub Actions `gate` remains PR-controlled. Until the Buildkite App check is required on protected `main`, this repository is not protected against an adversarial PR replacing its own Actions workflow.

## Cost and maintenance

As of 2026-10-01, the connected Buildkite organization is on a 26-day evaluation trial and scheduled to switch to Platform Free on 28 Oct 2026. Buildkite Free includes up to 2,000 Linux vCPU minutes per month and only the Small Linux shape; it is quota-limited, not unlimited. The dedicated verifier uses the existing `linux-small` queue. Confirm current terms and usage rates at [Buildkite pricing](https://buildkite.com/pricing/) and [Linux Hosted Agents pricing](https://buildkite.com/platform/pipelines/hosting-options/linux-hosted-agents/). Cloudflare Workers AI Free has a recurring 10,000 Neurons/day allocation; Free requests fail after quota and the runner has no paid fallback. Confirm current terms at [Cloudflare pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/).

When `policy.yaml` or either lockfile changes, independently review the change and update the matching pinned SHA-256 in `pipeline.yml`, then update the Buildkite dashboard YAML from this repository. Keep this public trust repository's `main` branch protected from force pushes and deletion.
